# Phase 02 — Private, Versioned Resume Storage

**Status:** COMPLETE

**Started:** 2026-08-29

**Verified:** 2026-08-29

## Objective

Store PDF and DOCX resumes privately in Supabase Storage while PostgreSQL remains the authoritative source for ownership, versioning, approval state, deduplication, and audit metadata.

## Scope

- `public.resumes` as a tenant-owned child of `public.candidate_profiles`.
- A fixed private Supabase Storage bucket named `private-resumes`.
- PostgreSQL RLS and Storage object policies for authenticated owners.
- Runtime tests with two synthetic users and transactional cleanup.

No parsing, extracted text, AI, resume generation, frontend, API, workflow, or later-phase functionality is included.

## Model

- UUID identity and composite `(user_id, candidate_profile_id)` tenant FK.
- Independent positive versions per CandidateProfile.
- Statuses: `DRAFT`, `PROCESSING`, `READY`, `APPROVED`, `ARCHIVED`, `REJECTED`.
- PDF/DOCX MIME allowlist and size range from 1 byte through 10 MiB.
- Lowercase hexadecimal SHA-256 metadata.
- Exact-content deduplication scoped to user plus CandidateProfile.
- One non-deleted `APPROVED` Resume per CandidateProfile.
- Soft deletion for Resume metadata; no authenticated physical DELETE privilege.

## Expected Status Transitions

- `DRAFT -> PROCESSING -> READY -> APPROVED`
- `DRAFT | PROCESSING -> REJECTED`
- `READY -> REJECTED`
- `APPROVED -> ARCHIVED`
- A prior `ARCHIVED` version remains immutable history conceptually, although a workflow engine is deliberately not introduced in this phase.

Lifecycle timestamp triggers populate `approved_at` and `archived_at`. Transition orchestration is deferred.

## Approval Decision

For the MVP, `status = APPROVED` is also the active Resume pointer. A partial unique index allows at most one non-deleted approved Resume for each user and CandidateProfile. This avoids a second mutable pointer while preserving every previous version as `ARCHIVED`.

## Storage Layout

`user_id/candidate_profile_id/resume_id/v{version}/resume.{pdf|docx}`

The path is generated by PostgreSQL from authoritative IDs, version, and MIME type. Original filenames are metadata only and cannot control object identity. Storage policies additionally require an owner-visible matching `public.resumes` row, so security does not rely only on the path.

## Runtime Validation

- Linked preflight showed Phase 1 synchronized and only `20260829000200_phase2_private_resumes.sql` pending.
- `db push --dry-run` listed only the Phase 2 migration, with no seeds or roles.
- The migration was applied successfully; a final migration list showed Phase 1 and Phase 2 synchronized locally and remotely.
- `public.resumes` exists with RLS enabled and forced, fifteen constraints, nine indexes, and two triggers.
- The `private-resumes` bucket is private, limited to 10 MiB, and allows only declared PDF and DOCX MIME values.
- Three Resume policies cover owner SELECT/INSERT/UPDATE; authenticated physical DELETE remains revoked.
- Four Storage policies cover owner SELECT/INSERT/UPDATE/DELETE and require an exact owner-visible Resume metadata row.
- Two-user runtime tests validated own creation and access, inverse A/B isolation, cross-tenant FK rejection, version bounds and uniqueness, SHA-256 format, tenant-scoped deduplication, MIME/size limits, generated path protection, unregistered-path rejection, soft delete, approval rotation, and `updated_at`.
- Storage DELETE tests used Supabase Storage's transaction-local `storage.allow_delete_query` flag so RLS was evaluated without disabling the platform's permanent direct-delete safeguard.
- Remote schema lint reported no errors.

## Corrections During Validation

- A test initially used `INSERT ... SELECT` for A attempting B's object. Resume RLS returned zero source rows, so it did not exercise the Storage INSERT policy. The test was corrected to use B's deterministic synthetic path explicitly.
- A direct Storage DELETE initially hit `storage.protect_delete()` before exercising ownership. The test now enables the platform's API-scoped deletion flag locally inside the rollback-only transaction.
- The applied migration required no correction.

## Cleanup

The final test completed with `ROLLBACK`. A separate remote post-check found zero synthetic rows in `auth.users`, `public.profiles`, `public.candidate_profiles`, and `public.resumes`, plus zero synthetic objects in `storage.objects`.

Phase 2 is complete. Phase 3 has not started.
